# OI-3 — Chunk Sizing and Overlap Strategy

**Related:** ADR-0017 REQ-3
**Status:** DRAFT — reopened after measurement; requires ratification before Part 2 code
**Date:** 2026-08-15

---

## Context

ADR-0017 REQ-3 requires the AI correction pass to send bounded transcript
chunks with stable segment, utterance, and word IDs rather than processing a
full transcript in one call.

The original fixed-utterance proposal was superseded by measurement. A chunk
of 50 utterances produced a fully serialized input of approximately 15,000 to
83,500 estimated tokens because utterance length varies and the JSON envelope
contains opaque IDs, timestamps, confidence scores, and metadata. Chunk sizing
must therefore be budget-based and must measure the complete serialized
request.

The target values in this document are provisional. They must be measured
against actual serialized Etminan chunks before ratification, and the Part 2
code PR must include a measurement step confirming that every request remains
within the approved model context budget.

## 1. Chunk contract and identity

A chunk is a bounded, contiguous slice of complete transcript utterances. It
contains an editable body and, when available, read-only context from the
adjacent chunks. Each chunk includes:

- `pass_id`: deterministic ID for the correction pass, derived from the
  deposition ID and the recorded pass-start timestamp.
- `chunk_id`: deterministic ID derived from `pass_id`, chunk ordinal, and the
  editable word-ID range.
- `transcript_hash`: hash of the canonical transcript content at pass start.
- `chunk_hash`: hash of the editable word content in the chunk.
- `ordinal`: sequential position beginning at zero.
- Stable `segment_ids`, `utterance_ids`, and `word_ids` from the canonical
  Deepgram evidence.
- For each word: `word_id`, text, start and end timestamps, confidence, and an
  `editable` flag.

The IDs and hashes are generated by the application, never by the AI. They
bind proposals to the exact pass, transcript state, chunk, and editable
content used to generate them. The AI may propose corrections only against
word IDs present in the chunk with `editable: true`.

## 2. Budget-based chunk sizing

The primary sizing unit is editable words, not utterances. Word count is
measurable before serialization, while utterance length can range from a
single word to more than 200 words. Utterances remain the indivisible boundary
unit, but their count is not a request-size proxy.

| Parameter | Provisional value |
|---|---:|
| Target editable body | Approximately 300 words |
| Maximum editable body | 350 words (hard ceiling) |
| Leading overlap | Up to 50 read-only words |
| Trailing overlap | Up to 50 read-only words |
| Maximum serialized request | 100 KB |

The chunker fills the editable body with complete utterances until adding the
next utterance would exceed 350 editable words. That utterance begins the next
chunk. A single utterance exceeding 350 words must not be split; it requires a
reported oversize-utterance failure and must not be submitted without a
separately ratified handling rule.

No chunk may be submitted when its fully serialized request exceeds 100 KB.
The chunker must reduce the editable body at an earlier utterance boundary and
serialize again until it fits. If the smallest valid chunk still exceeds the
ceiling, processing stops and reports the failure.

## 3. Serialized request measurement (OI-3C)

The `words × 1.3` estimator is prohibited because it excludes the JSON
structure, opaque SHA-based identifiers, timestamps, confidence scores, prompt
content, and metadata overhead.

Before submission, the application measures the complete serialized request:

1. **Preferred:** use the provider's tokenizer on the exact serialized request
   JSON. An approved compatible tokenizer such as `tiktoken` may be used as a
   documented proxy when the provider does not supply local token counting.
2. **Fallback:** use the serialized byte count as a conservative proxy. At
   four bytes per token, 100 KB represents an approximate ceiling of 25,000
   tokens. A request larger than 100 KB is split further.

Both byte size and the available token count must be recorded as pass
telemetry. Prose word count alone is never sufficient to authorize submission.

## 4. Boundary preservation

Chunks never split an utterance. Utterance boundaries are the controlling
constraint for raw, unreconciled Deepgram output.

When speaker roles have already been reconciled and Q./A. roles are known, a
question and its immediately following answer must remain in the same editable
body. This Q./A. constraint is additional to utterance preservation and may
move the boundary earlier. The chunker must not infer Q./A. roles merely to
construct chunks from unreconciled output.

If preserving a known Q./A. pair would exceed either hard ceiling, processing
stops and reports a boundary-budget conflict; it does not silently split the
pair or submit an oversized request.

## 5. Read-only overlap and ownership

Leading overlap contains up to 50 words from the end of the prior editable
body. Trailing overlap contains up to 50 words from the start of the next
editable body. In both directions, the chunker includes complete utterances
until adding another would exceed 50 words; it never splits an utterance to
fill the overlap allowance.

Every overlap word is marked `editable: false`. Evidence from overlap may
support a proposal anchored in the editable body, but neither a correction
anchor nor any part of a multi-word correction range may lie in overlap.

Each editable word has exactly one editable owner across the full pass.
Overlap is context-only, so duplicate arbitration for the same editable token
is neither needed nor permitted as a normal merge mechanism.

## 6. Processing order (OI-3A)

Processing is sequential for v1. The application submits chunk N, receives
and validates its response, persists valid CorrectionObjects as pending ATIA
proposals, and only then submits chunk N+1. Chunks are never submitted in
parallel in v1.

## 7. Failure handling and restart (OI-3B)

On failure:

1. Stop immediately and do not submit remaining chunks.
2. Do not apply or persist corrections from the failed chunk.
3. Valid proposals from completed chunks remain pending; they do not alter the
   canonical transcript without reporter acceptance.
4. Report the failed chunk ordinal and a non-sensitive failure description.

On restart, recompute the canonical transcript hash:

- If it matches the pass's recorded `transcript_hash`, resume at the failed
  chunk and do not reprocess completed chunks.
- If it differs, invalidate the pass and its pending proposals, notify the
  reporter, and restart at chunk 0 with a new `pass_id`, `transcript_hash`, and
  deterministic chunk set.

The application must persist each pass and chunk's deterministic identity,
hashes, ordinal, and completion status to support this decision.

## 8. Chunk validation before submission

A chunk failing any check must not be sent:

- **V1:** Every `word_id` exists in the canonical Deepgram store for the
  transcript.
- **V2:** Every `utterance_id` exists in the canonical store.
- **V3:** Every `segment_id` exists in the canonical store.
- **V4:** No `word_id` appears more than once in the chunk's words array.
- **V5:** Editable-body utterances are contiguous with no ordinal gaps.
- **V6:** Every overlap utterance and word has `editable: false`.
- **V7:** Every editable-body utterance and word has `editable: true`, and
  every editable word has exactly one owner in the pass.
- **V8:** Editable word count is no greater than 350.
- **V9:** The fully serialized request is no greater than 100 KB and satisfies
  the approved token budget when tokenizer measurement is available.
- **V10:** No utterance is split at a boundary. When roles are known, no Q./A.
  pair is split; when roles are unknown, no Q./A. role inference is attempted.

## 9. AI response validation

Before persisting any CorrectionObject, the application validates:

- **R1:** Response `chunk_id` matches the submitted `chunk_id`.
- **R2:** Every correction `word_id` exists in the chunk's words array.
- **R3:** Every correction `word_id` has `editable: true`.
- **R4:** Every `end_word_id`, when present, exists in the chunk, has
  `editable: true`, and follows `word_id` in transcript order.
- **R5:** No two proposed correction ranges overlap.
- **R6:** Every `correction_type` is permitted: `spelling`, `punctuation`,
  `capitalization`, `word_replacement`, `inaudible`, `speaker_assignment`, or
  `structure`.
- **R7:** Every `confidence_score` is numeric and between zero and one.
- **R8:** Every evidence source is permitted: `transcript`, `keyterm`,
  `case_context`, or `case_material`.
- **R9:** `proposed_value` is non-empty, except an explicitly typed deletion
  may use an empty string.
- **R10:** The response contains no free-form prose, rewritten utterances, or
  content outside the structured corrections contract.

If R1 fails, the entire response is rejected. Any individual proposal failing
R2–R10 is discarded and reported. In v1, an `[inaudible]` proposal is also
rejected unless the relevant word data includes acoustic evidence such as low
confidence or an explicit inaudible marker.

## 10. Decisions and ratification status

| Decision | Outcome |
|---|---|
| OI-3A — Processing order | Sequential for v1 |
| OI-3B — Restart granularity | Resume failed chunk only when `transcript_hash` is unchanged; otherwise invalidate and restart at chunk 0 |
| OI-3C — Request measurement | Measure the fully serialized request; provider tokenizer preferred, 100 KB byte ceiling as fallback |

OI-3 remains **unratified**. The approximately 300-word target, 350-word hard
ceiling, overlap allowance, and 100 KB serialized ceiling must be verified by
measurement before ADR-0017 or this implementation design may be ratified.
